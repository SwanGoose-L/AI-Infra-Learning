**1:59｜数据收集**

我们先来看如何通过预训练得到一个基础模型。

首先，需要收集大量数据。

这里展示了一个“数据混合”的例子，来自 Meta 发布 LLaMA 基础模型时的论文。

![Pasted image 20261028180546](../../../assets/images/Pasted%20image%2020261028180546.png)

**2:31**

这些数据会混合在一起，再按照给定比例进行采样，从而构成 GPT 的训练集。

不过，在真正用这些数据进行训练之前，还需要完成一个预处理步骤：**分词，也就是 tokenization**。

![Pasted image 20261028180621](../../../assets/images/Pasted%20image%2020261028180621.png)

本质上，这一步是把从互联网上抓取的原始文本，转换成整数序列，因为 GPT 原生处理的就是这种表示形式。


**2:53**

文本片段与 token 及其对应整数之间的转换是无损的。完成这一步有多种算法。

例如，<mark style="background:#d2cbff">一种常见方法是字节对编码，也就是 BPE。它会反复合并文本片段，将它们组织成 token。</mark>

这里展示了一些 token 对应的文本片段，以及最终真正输入 Transformer 的原始整数序列。

**4:57**

那么，真正进行预训练时，会发生什么？

概括来说，我们会取出 token，把它们组织成数据批次。这些数组随后会输入 Transformer。

数组的形状是 **B × T**。B 是批次大小，每一行都是一个独立样本；T 是最大上下文长度。


![Pasted image 20261028181126](../../../assets/images/Pasted%20image%2020261028181126.png)

在这张示意图里，上下文长度只有 10，但实际可能是 2,000、4,000 等。因此，每一行实际上都非常长。

我们把文档装进这些行中，并使用特殊的“文本结束”token 将它们分隔开。这基本上是在告诉 Transformer：一篇新文档从哪里开始。

这里有几篇示例文档，我把它们展开，放进了输入中。

**5:41**

现在，我们要把所有这些数字输入 Transformer。

我先聚焦到其中一个格子，不过图里的每个格子都会发生同样的事情。

来看绿色的格子。它会查看此前的所有 token，也就是黄色的那些。我们把整个上下文输入 Transformer 神经网络，让它尝试预测序列中的下一个 token，也就是图里的红色 token。

![Pasted image 20261028181207](../../../assets/images/Pasted%20image%2020261028181207.png)

**6:08**

很遗憾，我没有足够时间详细介绍 Transformer 的网络结构。对于这次演讲，你可以暂时把它看作一大块神经网络，通常包含几百亿个参数。

当我调整这些参数时，每个格子所对应的预测概率分布都会发生细微变化。

例如，如果词表中有 50,257 个 token，那么输出就会包含同样数量的数字，因为我们需要为下一个可能出现的 token 指定一个概率分布。

也就是说，我们要给每一种可能的后续 token 分配一个概率。

在这个具体例子里，对这个特定格子而言，下一个整数应当是 513。因此，我们可以利用这个已知答案作为监督信号，更新 Transformer 的权重。

我们会在所有格子上并行执行这一过程，不断更换数据批次，让 Transformer 越来越准确地预测序列中的下一个 token。

**7:03**

我再用一个更具体的例子，展示训练这类模型时会发生什么。

这个例子来自《纽约时报》。他们用莎士比亚的作品训练了一个小型 GPT。

![Pasted image 20261028181317](../../../assets/images/Pasted%20image%2020261028181317.png)

这里是一小段莎士比亚文本，他们用这些内容训练 GPT。

最初，模型刚初始化时，权重完全随机，输出也完全随机。但随着训练时间越来越长，模型生成的样本会越来越连贯、越来越一致。

当然，采样过程是这样的：先预测下一个 token 的概率分布，从这个分布中采样一个 token，再把它放回输入中继续预测。这样就能生成很长的序列。

到最后，你会发现 Transformer 已经学会了单词，学会了在哪里放空格、在哪里放逗号，等等。

随着时间推移，预测越来越合理。

![Pasted image 20261028181435](../../../assets/images/Pasted%20image%2020261028181435.png)

这些曲线就是进行模型预训练时，我们通常会观察的内容。实际上，我们关注的是损失函数如何随训练时间变化。损失越低，就意味着 Transformer 为序列中下一个正确整数分配的概率越高。

**8:06｜基础模型会学到强大的通用表征**

假设我们花了一个月，终于把模型训练好了，接下来能拿它做什么？

整个研究领域首先注意到的是：这些模型在进行语言建模的过程中，基本上会学到非常强大的通用表征。

因此，我们可以非常高效地对它们进行微调，使其适应各种我们感兴趣的下游任务。

![Pasted image 20261028181544](../../../assets/images/Pasted%20image%2020261028181544.png)

举个例子，如果你想做情感分类，以前的做法是：收集一批正面和负面样本，然后专门训练一个自然语言处理模型。

新的做法则是：先把情感分类放到一边，去进行大语言模型预训练，训练一个大型 Transformer。

之后，即使你手头只有少量示例，也能非常高效地把模型微调到情感分类任务上。

这种方法在实践中效果很好。

**8:48**

原因在于，Transformer 在完成语言建模任务时，被迫同时学习大量不同的任务。

因为，要预测下一个 token，它就必须理解很多东西，包括文本结构，以及文本中涉及的各种概念。

这就是 GPT-1 阶段的情况。

**9:09**

到了 GPT-2 前后，人们发现，甚至不必微调（fine-tuning），也可以通过提示（prompting）非常有效地使用这些模型。

它们是语言模型，想做的是补全文档。因此，你可以构造一些“虚拟文档”，诱导它们去执行特定任务。

![Pasted image 20261028181702](../../../assets/images/Pasted%20image%2020261028181702.png)

例如，在这个例子中，我们先给出一段文章，再放入几组“问题—答案、问题—答案、问题—答案”。

**9:31**

这叫作 **少样本提示，也就是 few-shot prompt**。

然后，我们只写出一个问题。当 Transformer 尝试补全文档时，它实际上就会回答这个问题。

这是对基础模型进行提示工程的一个例子：让它相信自己正在模仿、续写一篇文档，从而让它执行某项任务。

**9:45**

我认为，这开启了一个更重视提示、而不只是微调的时代。

人们发现，即使不进行神经网络训练、不做微调，仅靠精心设计的提示词，也能非常出色地解决很多问题。

从那以后，各方训练的基础模型如进化树般蓬勃发展，形成了百花齐放的研究生态。

![Pasted image 20261028181859](../../../assets/images/Pasted%20image%2020261028181859.png)

**10:02**

并非所有模型都可以获得。

例如，GPT-4 的基础模型从未公开。你通过 API 使用的 GPT-4，并不是基础模型，而是经过调优的助手模型。稍后我们会介绍如何得到这种助手模型。

GPT-3 的基础模型可以通过 API 使用，名字叫 **davinci**。GPT-2 的基础模型甚至连权重都公开在我们的 GitHub 仓库里。

不过，目前能够获得的最佳基础模型，可能是 Meta 的 LLaMA 系列，尽管它没有商业使用许可。

> 注：转写中的 “Devanshi” 在此校正为模型名 davinci。

**10:32**

这里需要强调一点：**基础模型本身不具备助手功能。**

它们的设计初衷不是回答你的问题，而是完成补全文档任务。

如果你让它“写一首关于面包和奶酪的诗”，它可能会用更多问题来回应，因为它正在补全自己认为正在阅读的那种文档。

![Pasted image 20261028182216](../../../assets/images/Pasted%20image%2020261028182216.png)

不过，对于基础模型，你可以采用一种更容易奏效的提示方式。

例如，你写：“下面是一首关于面包和奶酪的诗：”

在这种情况下，它就更可能正确地续写。

你甚至可以诱导基础模型扮演助手。

![Pasted image 20261028192101](../../../assets/images/Pasted%20image%2020261028192101.png)

方法是构造一个特定的少样本提示，让它看起来像是一份记录人类与助手之间信息交流的文档。

然后，在文档最下方放入你的问题。基础模型就会在这个上下文条件下，扮演一个乐于助人的助手，并给出回答。

但这种方法不太可靠，在实践中效果也不算特别好，虽然技术上确实可行。

**11:26**

因此，我们采用另一条路径，来训练真正的 GPT 助手，而不只是会补全文档的基础模型。

这就进入了 **监督微调** 阶段。

![Pasted image 20261028192249](../../../assets/images/Pasted%20image%2020261028192249.png)

在监督微调阶段，我们会收集规模较小、质量较高的数据集。

具体来说，我们会请人工标注人员收集这样的数据：一个提示，以及与之对应的理想回答。通常会收集几万条左右的示例。

接下来，我们仍然在这些数据上进行语言建模。从算法上说，并没有什么变化，只是换了训练集。

原先使用的是互联网文档，特点是数量多、质量相对较低。现在换成了经过人工整理的“提示—回答”数据，特点是数量少、质量高。

我们仍然进行语言建模。训练完成后，就得到了一个 **SFT 模型**，也就是监督微调模型。

这些模型实际上已经可以部署。它们已经是真正的助手，并且在一定程度上能够正常工作。

**12:22**

我来展示一下示范数据可能是什么样子。

![Pasted image 20261028192352](../../../assets/images/Pasted%20image%2020261028192352.png)

这是人工标注人员可能编写的一条数据。

先有一个提示，例如：“你能简要介绍一下 monopsony，也就是买方垄断这个术语的重要性吗？”

然后，标注人员再写出一个理想回答。

编写回答时，他们需要遵循详细的标注规范，并被要求做到：**有帮助、真实、无害**。

这里展示了这些标注说明。你们大概看不清，我也看不清，但它们确实很长。

这些工作就是由人们按照说明，努力完成各种提示对应的回答。

这就是数据集的样子。用它们可以训练模型，并且能够取得一定效果。

**12:59**

不过，训练流程还可以继续，进入 **RLHF，也就是基于人类反馈的强化学习**。

![Pasted image 20261028192553](../../../assets/images/Pasted%20image%2020261028192553.png)

它包含==🟣**奖励建模和强化学习**==两个部分。

我先介绍这两个阶段，之后再解释为什么值得增加这些步骤，以及它们与 SFT 模型相比有什么不同。

**13:16｜奖励模型的数据集**

在奖励建模阶段，我们会改变数据收集方式，开始收集比较数据。

这里展示了数据集的一个例子。

![Pasted image 20261028192756](../../../assets/images/Pasted%20image%2020261028192756.png)

上方仍然是同一个提示：要求助手编写一个程序或函数，用于检查给定字符串是否为回文。

接着，我们使用已经训练好的 SFT 模型，生成多个回答。

在这个例子里，模型生成了三个回答。然后，我们请人对这些回答进行排序。

如果仔细研究一下，你就会发现，比较这些回答有时是非常困难的事情。仅仅评估一组提示及其候选回答，就可能花费数小时。

![Pasted image 20261028192844](../../../assets/images/Pasted%20image%2020261028192844.png)

不过，假设我们最终判断出，某个回答明显比其他回答更好，等等，于是就能给它们排出顺序。

之后，我们可以把所有候选回答两两配对，构造一个非常类似于二分类的问题。

**14:10｜奖励模型的训练**

具体来说，我们把提示按行排列。这里三行中的提示完全相同，只是后面接的回答不同。

黄色的 token 来自 SFT 模型生成的回答。

![](../../../assets/images/Pasted%20image%2020261028192951.png)

接下来，我们在结尾添加一个特殊的“奖励读出”token，并且只在这个绿色 token 所在的位置，对 Transformer 施加监督。

Transformer 会预测一个奖励数值，用来表示：对于这个提示，这个回答有多好。也就是说，它会猜测每个回答的质量。

当它为每个回答都给出一个分数后，我们还掌握着人工提供的真实排序。

于是，我们就可以要求某些回答的分数高于其他回答。我们把这种要求写成损失函数，训练模型，使它预测的奖励分数与人工比较得到的排序保持一致。

这就是奖励模型的训练方式。有了它，我们就能为某个提示下的回答质量打分。

**15:02**

得到奖励模型之后，我们还不能把它作为助手直接部署，因为它本身并不是一个特别有用的助手。

但对于接下来的**强化学习**阶段，它非常有用。

因为现在，对于任意一个提示，我们都可以为任意一个回答评估质量。

![](../../../assets/images/Pasted%20image%2020261028193441.png)

进行强化学习时，我们会再次收集大量提示，然后根据奖励模型开展强化学习。

具体过程是这样的。

![](../../../assets/images/Pasted%20image%2020261028193519.png)

先取出一个提示，把它重复放在多行中。

接着，使用我们希望训练的模型（它由 SFT 模型初始化），生成图中黄色的回答。

随后，再次添加奖励 token，并使用奖励模型读出相应的奖励分数。

此时，奖励模型保持固定，不再发生变化。奖励模型会告诉我们，<u>每个提示所对应的每个回答质量如何。</u>

接下来，我们基本上可以使用同样的语言建模损失函数，但这次训练针对的是黄色的回答 token，并且要根据奖励模型提供的分数，对语言建模目标进行加权。

例如，在第一行中，奖励模型认为这是一个得分相当高的回答。于是，第一行里采样得到的所有 token 都会受到强化，将来出现的概率会提高。

相反，在第二行中，奖励模型很不喜欢这个回答，给出的分数是 −1.2。因此，第二行里采样得到的每个 token，将来出现的概率都会略微降低。

> 注：原转写此处写的是“概率略微提高”，与前后逻辑相反。这里按上下文译为“降低”。

我们在许多提示、许多数据批次上反复执行这一过程，最终得到一个能够生成这些黄色 token 的策略。这样一来，它生成的回答，基本上都能在前一阶段训练好的奖励模型那里获得较高分数。

这就是 RLHF 的整个流程。

最后，我们得到一个可以部署的模型。

**16:58**

例如，ChatGPT 就是一个 RLHF 模型。而你可能接触到的另一些模型，例如 Vicuna-13B 等，则属于 SFT 模型。

所以，我们有基础模型、SFT 模型和 RLHF 模型。这就是目前的大致情况。

**17:12**

那么，为什么要做 RLHF？一个不太令人兴奋、但很直接的答案是：**它的效果更好。**

![](../../../assets/images/Pasted%20image%2020261028193839.png)

这里的数据来自 InstructGPT 论文。在这些已经有些时间的实验中，标为 PPO 的模型就是 RLHF 模型。

把它们的回答交给人类进行比较时，可以看到，人们在很多比较中都更偏爱它们。

**17:30**

与 SFT 模型相比，与通过提示扮演助手的基础模型相比，人们通常更喜欢 RLHF 模型生成的内容。它就是效果更好。

但你可能会追问：为什么效果更好？我认为，研究界还没有就某个特别有说服力的单一解释达成共识，不过我可以提出一个可能的原因。

这与“比较”和“生成”在难度上的不对称有关。

我们以写俳句为例。

![](../../../assets/images/Pasted%20image%2020261028193951.png)

假设我让模型写一首关于回形针的俳句。如果你是一位负责制作训练数据的标注人员，正在为 SFT 阶段收集数据，那么你该如何写出一首关于回形针的优秀俳句？

你可能不太擅长这件事。但如果我给你几首俳句，你可能能够判断，有些明显比其他的更好。

**判断哪个更好，是一项容易得多的任务。** 这种不对称意味着：通过比较，我们可能更容易发挥人类的判断能力，从而训练出稍微更好的模型。

**18:33｜模式坍塌**

不过，在某些方面，RLHF 模型并不一定全面优于基础模型。

尤其是，我们观察到它们会损失一些熵。这意味着，输出分布会变得更集中、更尖锐。与基础模型相比，它们生成的样本可能缺少变化。

![](../../../assets/images/Pasted%20image%2020261028194139.png)

基础模型的熵较高，因此能够给出更多样的输出。

**19:00**

例如，有一种场景，我仍然更喜欢使用基础模型：你已经有了若干个事物，想继续生成更多类似的事物。

这是我临时构造的一个例子。我想生成一些很酷的宝可梦名字，于是给它七个宝可梦名字，再让基础模型继续补全文档。它就给出了许多新的宝可梦名字。

![](../../../assets/images/Pasted%20image%2020261028194205.png)

这些名字是虚构的。我尝试查过，我认为它们并不是真实存在的宝可梦。

我觉得基础模型很擅长这类任务，因为它仍然具有较高的熵。它会给你很多多样、有趣的新东西，而且这些东西与之前提供的示例相似。

**19:41**

说了这么多，这里列出的是目前大家可能能够使用的一些助手模型。

伯克利有一个团队，对许多现有助手模型进行了排名，并给出了类似 Elo 的等级分。

目前表现最好的模型当然包括 GPT-4（我认为它遥遥领先），之后是 Claude、GPT-3.5，以及其他一些模型。

其中有些模型可能提供权重，例如 Vicuna、Koala 等。

这里的前三行都是 RLHF 模型。据我了解，其他模型应该都是 SFT 模型。

![](../../../assets/images/Pasted%20image%2020261028194252.png)

以上就是从整体上看，我们如何训练这些模型。

**20:15**

现在，我想换个方向，看看如何更好地把 GPT 助手模型应用到你们的问题中。

我想用一个具体例子来展开。假设你正在写一篇文章或博客，准备在结尾写下这样一句话：“加利福尼亚州的人口是阿拉斯加州的 53 倍。” 也就是说，出于某种原因，你想比较这两个州的人口。

请想一想，为了写出这一句最终文本，你的大脑里究竟发生了多少内心独白、多少工具调用，以及多少计算工作。

你的思考过程可能是这样的。

![](../../../assets/images/Pasted%20image%2020261028194335.png)

“接下来，我要在博客里比较这两个州的人口。” 
“首先，我显然需要知道这两个州各有多少人口。” 
“我大概不记得这些数字。”

也就是说，我知道自己知道什么、不知道什么，对自己的知识状态有所了解。

然后，我会使用工具，打开维基百科，查找加利福尼亚州和阿拉斯加州的人口。

接下来，我知道应该把两个数字相除。但我也知道，想在脑子里算出 39.2 除以 0.74，很可能算不出来。这不是我擅长的心算任务。因此，我会使用计算器，输入数字，看到结果大约是 53。

然后，我可能会反思一下，在脑子里做个合理性检查。

“53 倍合理吗？”
“这个比值挺大，不过加利福尼亚州是人口最多的州，所以看起来也说得通。”

现在，我已经有了需要的信息，接下来就进入写作中更有创造性的部分。

我可能开始写：“加利福尼亚州有 53 倍更多的……”

然后我会想：“这个表达太别扭了，删掉，重新写。”写作时，我仿佛还有另一套独立过程，在审视自己正在写的内容，判断它是否合适。

我可能删除一些内容，换一种表述，最后才对写出来的句子感到满意。总之，当你写出这样一句话时，背后的内心独白其实包含了大量活动。

**22:21**

但是，当我们用这句话训练 GPT 时，从 GPT 的角度看，它是什么样子？

它只是一串 token。GPT 读取或生成这些 token 时，就是一块、一块、一块地处理；对每个 token，所投入的计算量大致相同。

这些 Transformer 并不是很浅的网络，它们大约有 80 层神经网络计算。不过，这样的计算深度仍然有限。

Transformer 会尽力模仿这句话，但它所经历的过程，显然与你刚才的思考过程很不一样。

![](../../../assets/images/Pasted%20image%2020261028194550.png)

特别是，我们最终产出的文字会被放进数据集，再输入大语言模型。但在这些成品中，所有内心对话都已经被完全剥离了。

而且，与你不同，GPT 会在每个 token 上花费同样多的计算量。因此，你不能指望它在单个 token 上完成过多的工作。

**23:13**

更具体地说，这些 Transformer 基本上就像 token 模拟器。它们不知道自己不知道什么，只是在模仿下一个 token。它们不知道自己擅长什么、不擅长什么，只是在尽力模仿下一个 token。

它们不会在生成过程中主动反思，不会检查是否合理，也不会沿途纠正自己的错误。

默认情况下，它们只是对 token 序列进行采样。它们脑子里没有另外一条独立的内心独白，去评估当前发生的事情。

不过，我认为，它们也有一些认知优势。

**23:48**

首先，它们确实在非常广泛的领域里储存了大量事实性知识，因为它们可能有几百亿个参数。这意味着有很大的存储容量，可以容纳大量事实。

此外，我认为它们还具有相对较大、而且“完美”的工作记忆。只要信息能放进上下文窗口，Transformer 就可以通过内部的自注意力机制立即访问它。

因此，这是一种容量有限、但可以直接访问的“完美记忆”。它可以无损地记住上下文窗口内的内容。

这就是我对两者的比较。

**24:22**

我之所以讲这些，是因为我认为，在很大程度上，提示工程就是在弥补这两种架构——我们的大脑和大语言模型的“大脑”——之间的认知差异。

你几乎可以从这个角度理解提示工程。

**24:39**

来看一个人们发现实践效果不错的方法。

特别是当任务需要推理时，你不能指望 Transformer 在每个 token 上完成大量推理。

你必须把推理过程分散到更多 token 中。

例如，你不能给 Transformer 一个非常复杂的问题，却期待它只用一个 token 就给出答案。它没有足够的计算时间。

我有时喜欢这样说：**“这些 Transformer 需要用 token 来思考。”**

![](../../../assets/images/Pasted%20image%2020261028194814.png)

因此，有些方法效果很好。例如，你可以使用少样本提示，展示在回答问题时应该写出解题过程。

给出几个例子后，Transformer 就会模仿这个模板，而在评测中，它通常也确实会表现得更好。

此外，你还可以直接说：“让我们一步一步地思考。” 这样也能引导 Transformer 展示解题过程。

当它进入这种展示过程的模式后，就不需要把那么多计算工作挤进每个 token 里。由于它能够把推理放慢、逐步展开，成功的可能性就会提高。

**25:46｜综合多次尝试**

另一个例子叫作 **自一致性，self-consistency**。

刚才我们看到，人类可以先开始写，如果写得不合适，就再试一次；也可以尝试很多次，然后选择效果最好的一次。

在这类方法中，你不会只采样一次，而是会采样多次。然后，再通过某种方法，找出其中较好的结果，只保留这些样本，或者进行多数投票，等等。

Transformer 在预测下一个 token 时，和你一样，也可能运气不好，采样出一个不太合适的 token，结果在推理上走进死胡同。但与你不同，它无法从那里恢复过来。

![](../../../assets/images/Pasted%20image%2020261028195023.png)

它已经采样出的每个 token，都会成为既定内容。因此，即使它已经“知道”这条序列不会得到好的结果，也还是会继续写下去。

所以，要给它回头检查的机会，或者让它通过多次采样，尝试其他路径。

**26:40｜要求模型反思**

还有一种方法。事实证明，大语言模型其实能够知道自己什么时候搞砸了。

![](../../../assets/images/Pasted%20image%2020261028195104.png)

例如，你要求模型写一首不押韵的诗，它可能给了你一首诗，但这首诗实际上押韵。

不过，尤其对于 GPT-4 这样较大的模型，你可以直接问：“你满足要求了吗？”

实际上，GPT-4 很清楚，自己并没有满足要求。只是它刚才采样时运气不好。

它会告诉你：“没有，我刚才确实没有满足要求。让我再试一次。”

但是，如果你不提示它，它并不知道应该回头检查。你必须在提示中补上这一点，让它检查自己的结果。如果你不要求它检查，它就不会主动检查。它只是一个 token 模拟器。

**27:28**

更广泛地说，我认为，这些方法中的很多，都可以归入一个方向：**重新构建我们的“系统 2”思维。**

你可能熟悉人类的“系统 1”和“系统 2”思维。

系统 1 是快速、自动的过程。我认为，它对应于大语言模型直接采样 token。

系统 2 则是大脑中更缓慢、更审慎、负责规划的部分。

![](../../../assets/images/Pasted%20image%2020261028195203.png)

这里有一篇论文，实际上就是上周刚发布的，因为这个领域正在飞速发展。

它叫作 **Tree of Thoughts，思维树**。作者提出：对于一个给定提示，同时维护多个候选续写，并在过程中不断给它们打分，保留那些进展较好的路径。

**28:08**

很多人都在探索提示工程，试图把我们大脑拥有的一些能力，也带给大语言模型。

不过，这里有一点需要说明：这并不只是一个提示。实际上，它是提示与一些 Python 胶水代码结合起来的系统。

因为你需要维护多个提示，还要运行某种树搜索算法，来判断接下来扩展哪些提示、哪些分支，等等。

这是 Python 胶水代码与单个提示之间的配合：这些提示会在 while 循环或更大的算法中被反复调用。

**28:38**

我认为，这与 AlphaGo 之间也有一个很有意思的对应关系。

AlphaGo 下围棋时，有一个决定下一步落子的策略。这个策略最初是通过模仿人类训练出来的。

但除了这个策略，它还会执行蒙特卡洛树搜索。也就是说，它会在“脑海”里推演多种可能性，评估这些可能性，只保留效果较好的路径。

如果这样类比的话，我认为这就相当于文本领域的 AlphaGo。

**29:08**

与思维树类似，人们正在开始探索更一般的方法。

它不再只是一个简单的“提问—回答”提示，而更像是用 Python 胶水代码，把许多个提示串联起来。

右边展示的是一篇名为 **ReAct** 的论文中的例子。

它把对提示的回答组织为一连串的：“思考—行动—观察，思考—行动—观察……”

也就是说，为了回答问题，模型会展开一整套行动轨迹与思考过程。

在这些行动中，模型也可以使用工具。

![](../../../assets/images/Pasted%20image%2020261028195345.png)

左边展示的是 AutoGPT。顺便说一句，AutoGPT 最近获得了大量关注。不过，我仍然觉得，它在启发思路这方面很有意思。

这个项目允许大语言模型维护一个任务清单，并不断递归地分解任务。

我认为，目前它的实际效果还不太好，也不建议大家把它用于实际应用。不过，从未来发展方向的角度，它仍然值得借鉴和获得启发。

这就像是赋予模型“系统 2”思维。

**30:16**

接下来，还有一个我觉得很有意思的现象，几乎可以说是大语言模型的一种“心理特点”：

**大语言模型想做的是模仿，而不是取得成功。你想取得成功，就应该明确提出这个要求。**

这是什么意思？训练 Transformer 时，训练集中的内容质量可能覆盖整个水平范围。

例如，对于一道物理题，训练数据中可能有学生完全错误的解答，也可能有专家极其准确的解答。

模型知道低质量解答是什么样，也知道高质量解答是什么样。

但默认情况下，它想模仿所有这些内容，因为它接受的只是语言建模训练。因此，在实际使用时，你必须明确要求它给出好的表现。

![](../../../assets/images/Pasted%20image%2020261028195444.png)

在这篇论文的例子里，研究人员尝试了各种提示。“让我们一步一步地思考”很有效，因为它把推理分散到了多个 token 上。

但效果更好的说法是：“让我们一步一步地解决这个问题，<u>确保得到正确答案</u>。”

这相当于把“得到正确答案”也设为了生成条件。

它确实会让 Transformer 表现得更好，因为模型不再需要把一部分概率分配给低质量解答——虽然这听起来很荒唐。

总之，你完全可以明确要求它给出高水平的解决方案。

**31:37**

你可以说：“你是这个领域的顶尖专家。”  “假设你的智商是 120。”诸如此类。

不过，不要把智商要求得太高。如果你说智商是 400，那可能就超出了训练数据的分布。

或者，更糟的是，它可能恰好落入了另一类训练数据的分布，比如科幻内容。于是，模型可能开始带入某种科幻风格，或者开始角色扮演。

因此，你需要找到一个合适的智商水平。我觉得这里可能存在某种 U 形曲线。

**32:02｜工具使用与插件**

接下来，正如我们刚才看到的，人类解决问题时，知道自己擅长什么、不擅长什么，并会借助工具来完成计算。

对于大语言模型，你也可能希望采用同样的做法。具体来说，我们可以给它计算器、代码解释器，以及搜索等能力。实现这些能力的方法有很多。

![](../../../assets/images/Pasted%20image%2020261028195656.png)

不过，还是要记住：默认情况下，这些 Transformer 可能不知道自己不知道什么。

你甚至可能需要在提示中直接告诉它：“你不太擅长心算。每当你需要对很大的数字做加法、乘法或其他运算时，请使用这个计算器。” “下面是计算器的使用方法：使用这样的 token 组合……”

这些事情需要明确写出来。因为模型默认情况下，并不一定像你我一样，知道自己擅长什么、不擅长什么。

**32:54**

接下来，我认为还有一个非常有意思的方向。我们从一个完全依赖检索的世界，摆到了另一个极端：在大语言模型中，完全依赖模型自身的记忆。

但实际上，在这两者之间还有很大的空间，也就是 **检索增强模型**。它在实践中效果非常好。

正如我前面所说，Transformer 的上下文窗口就是它的工作记忆。如果你能把与任务相关的信息放进这个工作记忆，模型就能立即访问这些信息，因此往往会表现得非常好。

我认为，很多人都对 **检索增强生成，也就是 RAG** 非常感兴趣。

**33:28**

下面展示的是 LlamaIndex，它是一种可以连接多种不同类型数据的数据连接工具。

![](../../../assets/images/Pasted%20image%2020261028195924.png)

你可以为这些数据建立索引，让大语言模型能够访问它们。

目前逐渐形成的一套流程是这样的：先取出相关文档，将它们切成小块，为每一块生成嵌入表示，也就是用一个向量表示这一块数据。

接着，把这些向量存进向量数据库。在实际使用时，向向量数据库发出某种查询，取回可能与当前任务相关的文本块，把它们放进提示中，然后让模型生成回答。

这种方法在实践中可以取得相当好的效果。

**34:06**

我认为，这与你我解决问题的方式很相似。你可以完全依靠记忆来做事，而 Transformer 也确实具有非常庞大、广泛的记忆。

不过，<u>查阅原始文档也确实很有帮助</u>。每当你需要回到教材里查找某个知识点，或者回到某个软件库的文档里查阅用法时，Transformer 其实也很需要这样做。

你可能记得某个软件库文档中的一些内容，但真正查一下通常更好。

对模型也是如此。

**34:35｜约束式提示与采样**

接下来，我想简短介绍一下约束式提示。我也觉得这个方向很有意思。

它主要指一些强制大语言模型按照特定模板输出的技术。微软的 Guidance 就是一个例子。这里，我们要求大语言模型的输出必须是 JSON。

![](../../../assets/images/Pasted%20image%2020261028200056.png)

它实际上可以保证输出符合这种形式。因为它会直接干预 Transformer 输出的各种 token 的概率，锁定某些 token，让 Transformer 只负责填空。

你还可以进一步限制，这些空白位置中允许出现哪些内容。这可能非常有用。我认为，这种约束采样也极其值得关注。

接下来，我还想谈几句微调。

**35:20**

确实，仅靠提示工程（prompt engineering），你就能走得很远。

但你也可以考虑对模型进行微调。微调意味着，你实际上要改变模型的权重。如今，这件事在实践中正在变得更容易，因为最近出现了许多相关技术和配套软件库。

![](../../../assets/images/Pasted%20image%2020261028200158.png)

例如，LoRA 这类参数高效微调技术，使你只需要训练模型中很小的一部分参数。

模型的大部分保持在基础模型的状态，只有某些部分允许发生变化。

从实验结果来看，这种做法仍然很有效，而且因为只调整模型中的少量部分，成本会低得多。

这也意味着，由于模型的大部分参数被冻结，你可以用非常低的精度来计算这些部分。

因为它们不会通过梯度下降更新，所以整体效率也会提高很多。

此外，我们现在还有许多开源的高质量基础模型。

**36:10**

正如前面提到的，我认为目前 LLaMA 很不错，尽管据我所知，它现在没有商业使用许可。

不过，有几点需要记住。首先，微调在技术上复杂得多，需要更多专业知识，才能做好。

它需要人工标注人员来制作数据集，或者需要合成数据流水线，而这些流水线可能相当复杂。这一定会明显放慢你的迭代速度。

从整体上说，我认为 SFT 是可以实现的，因为你做的仍然是继续训练语言建模任务，相对直接。

但是，RLHF 在很大程度上仍然属于研究领域，让它正常工作要困难得多。

因此，我大概不会建议大家直接尝试自己从头实现一套 RLHF。这些方法相当不稳定，很难训练，在我看来，目前对初学者并不友好。而且，它们很可能还会继续快速变化。

**37:11｜默认建议**

因此，以下是我目前通常会给出的建议。

我会把你的任务分成两个主要部分，而且按这个顺序进行：

第一，先取得尽可能好的效果。

第二，再进行优化。

![](../../../assets/images/Pasted%20image%2020261028200512.png)

对于第一点，目前最好的效果来自 GPT-4。它是所有模型中能力最强的，而且优势非常明显。

使用尽可能详细的提示，包含充分的任务背景、相关信息和明确指令。你可以这样想：如果你把任务交给一个外包人员，而对方无法再发邮件向你追问，你会向他说明哪些事情？

但也要记住，外包人员是人类，有内心独白，也很聪明，等等；大语言模型并不具备完全相同的这些特点。因此，你几乎需要思考一下大语言模型的“心理”，据此设计适合它的提示。检索并补充任何相关的上下文和信息，把它们加入提示。

总的来说，可以参考各种提示工程技术。我在前面的幻灯片里介绍了一些，但这是一个很大的领域，我也建议大家到网上寻找更多提示工程方法。

这里有很多内容值得研究。

**38:13**

1. 尝试少样本示例。意思是：只要有可能，就不只是告诉它怎么做，还要给它看应该怎么做。因此，如果可以，就提供各种有助于模型真正理解你意思的示例。

2. 尝试使用工具和插件，把大语言模型本身难以完成的任务交出去。

3. 同时，不要只考虑一次提示和一次回答。还可以考虑提示链、反思机制，以及如何把它们连接起来；也可以考虑多次采样等方法。

**38:36**

最后，如果你认为已经把提示工程的潜力挖掘得差不多了——不过，我认为你应该在提示工程上多坚持一段时间——那么可以考虑针对自己的应用微调模型。但要做好准备：这一过程会慢得多，也复杂得多。

再往后，就是一个需要专家介入、方法脆弱、仍处于研究中的区域，也就是 RLHF。如果能够把它做好，目前它的效果确实比 SFT 略好。但我还是要强调，这是一件相当复杂的事情。

至于成本优化，可以尝试能力较低、规模较小的模型，或者缩短提示，等等。

**39:12**

我还想谈几句，我认为目前哪些应用场景比较适合大语言模型。特别要注意，如今的大语言模型仍然存在很多限制。因此，在设计任何应用时，都应该把这些限制考虑进去。这些限制本身就足以单独讲一场演讲，所以我没有时间全面展开。

模型可能存在偏见，可能编造或“幻觉”出信息，可能出现推理错误，也可能在某些整类应用中表现不佳。

它们存在知识截止时间，因此可能完全不知道某个日期之后的信息，例如 2021 年 9 月之后的信息。

它们也容易受到各种攻击。新的攻击方法几乎每天都会出现在 Twitter 上，包括提示注入、越狱攻击、数据投毒等。

因此，我目前的建议是：将大语言模型用于风险较低的应用，并始终结合人工监督。

![](../../../assets/images/Pasted%20image%2020261028200704.png)

把它们当作灵感和建议的来源，把它们想象成“副驾驶”。至于那种完全自主、被派到某个地方独立执行任务的智能体，目前还不清楚模型是否已经具备足够的能力。
